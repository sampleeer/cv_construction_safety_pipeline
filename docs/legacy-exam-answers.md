## 1. Определение больших данных. 3V of Big Data. Характеристики больших данных

**Источник:** `BD_2026_1.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Большие данные - это данные, которые невозможно эффективно хранить, обрабатывать и анализировать на одном узле за разумное время обычными средствами. Ключевая идея: нужен кластер, распределенное хранение, распределенные вычисления и специальные подходы к отказоустойчивости.
2. **Зачем нужно.** Big Data решает проблему роста объема, скорости поступления и разнообразия данных. Если данных слишком много для одной машины, если они приходят постоянно или имеют разные форматы, классическая БД или локальный скрипт перестают быть достаточными.
3. **Ключевые компоненты.** Базовая модель описывается через 3V: Volume - объем данных; Velocity - скорость поступления и необходимость быстрой обработки; Variety - разнообразие форматов. Часто добавляют Veracity - достоверность/шумность данных, и Value - полезность результата. На уровне инфраструктуры нужны кластер, распределенное хранилище, вычислительный фреймворк, мониторинг и механизмы отказоустойчивости.
4. **Как работает пошагово.** Сначала данные поступают из источников: логи, транзакции, события, файлы, сенсоры. Затем они попадают в слой ingestion: batch-загрузка, streaming или микропакеты. Потом данные сохраняются в HDFS, object storage, Data Lake, ClickHouse, Greenplum или другую систему. Далее Spark/MapReduce/Kafka Streams выполняют обработку. Затем результат попадает в витрину, ML-модель, BI-систему или API.
5. **Плюсы.** Можно обрабатывать терабайты и петабайты данных, масштабироваться горизонтально, строить аналитику почти в реальном времени, объединять разнородные источники и повышать устойчивость за счет репликации.
6. **Минусы/ограничения.** Высокая сложность инфраструктуры, необходимость DevOps/DataOps-компетенций, дорогая отладка, сетевые задержки, проблемы качества данных, сложность обеспечения согласованности и безопасности.
7. **Реальный кейс.** Онлайн-ритейл собирает клики, покупки, поисковые запросы, отзывы и логи доставки. Эти данные обрабатываются в Spark, события идут через Kafka, результаты сохраняются в ClickHouse для аналитики и используются ML-моделью рекомендаций.

## 2. Grid технология. Определение. Архитектура

**Источник:** `BD_2026_1.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Grid - это подход к распределенным вычислениям, при котором вычислительные ресурсы нескольких узлов объединяются для решения крупной задачи. В лекции отдельно упоминается Gfarm как пример системы обработки данных большого масштаба.
2. **Зачем нужно.** Grid нужен, когда одна машина не справляется по CPU, памяти или диску, а задачу можно разбить на части. Проблема - эффективно распределить вычисления и данные между узлами.
3. **Архитектура.** Типичная Grid-система включает узлы вычислений, распределенную файловую систему, планировщик заданий, механизм передачи данных и мониторинг. Важный принцип из лекции: Code-to-Data, то есть переносить код к данным, а не тащить большие данные по сети.
4. **Как работает пошагово.** Пользователь отправляет задачу. Планировщик определяет, где лежат нужные данные и какие узлы свободны. Код запускается рядом с данными. Каждый узел обрабатывает свою часть. Затем результаты агрегируются и возвращаются пользователю или сохраняются в хранилище.
5. **Плюсы.** Горизонтальное масштабирование, параллелизм, возможность использовать много относительно дешевых машин, меньше сетевого трафика при Code-to-Data.
6. **Минусы/ограничения.** Сложное управление задачами, зависимость от сети, неоднородность ресурсов, проблемы с отказами отдельных узлов, сложность отладки распределенных задач.
7. **Реальный кейс.** Научная обработка больших наборов данных: моделирование физических процессов, геномика, обработка спутниковых снимков. Данные лежат на распределенной файловой системе, вычисления отправляются на узлы, где эти данные доступны.

## 3. Примеры задач больших данных с описанием анализа

**Источник:** `BD_2026_1.pdf`, `Базы данных в MLOps.pdf`.

1. **Определение.** Задача больших данных - это прикладная задача, где объем, скорость или разнообразие данных требуют распределенной обработки и специальной архитектуры.
2. **Зачем нужно.** Такие задачи нужны бизнесу и науке для принятия решений, автоматизации, прогнозирования, обнаружения аномалий и персонализации.
3. **Ключевые компоненты.** Обычно есть источники данных, ingestion, хранилище, обработка, аналитическая модель, витрина или API, мониторинг качества.
4. **Как работает пошагово.** Пример 1: антифрод. События платежей идут в Kafka, Spark Streaming считает признаки, модель определяет риск, результат пишется в БД и отдается платежному сервису. Пример 2: рекомендации. Логи просмотров и покупок собираются в Data Lake, Spark агрегирует историю, MLlib или отдельная модель обучается, витрина рекомендаций обновляется. Пример 3: мониторинг инфраструктуры. Логи и метрики поступают постоянно, ClickHouse хранит временные ряды, аналитика ищет аномалии.
5. **Плюсы.** Автоматизация решений, быстрая аналитика, возможность обрабатывать данные целиком, а не маленькую выборку.
6. **Минусы/ограничения.** Данные могут быть грязными, задержки ingestion влияют на результат, модель может устаревать, инфраструктура требует поддержки.
7. **Реальный кейс.** Банк анализирует транзакции: хранит историю в распределенном хранилище, поток новых транзакций обрабатывает через Kafka/Spark, а подозрительные операции блокирует или отправляет на дополнительную проверку.

## 4. Модели хранения данных. Теорема CAP. ACID свойства

**Источник:** `Базы данных в MLOps.pdf`, `BD_2026_1.pdf`.

1. **Определение.** Модели хранения данных описывают, как данные организованы и как к ним обращаться: реляционная модель, key-value, document, column-family, graph, columnar OLAP, файловое хранение. CAP говорит, что в распределенной системе при сетевом разделении нельзя одновременно идеально обеспечить Consistency, Availability и Partition tolerance. ACID - свойства транзакций: Atomicity, Consistency, Isolation, Durability.
2. **Зачем нужно.** Выбор модели хранения определяет скорость чтения/записи, масштабируемость, надежность, согласованность и удобство аналитики.
3. **Ключевые компоненты.** Реляционные БД используют таблицы, строки, столбцы, ключи и SQL. NoSQL может использовать документы, ключ-значение, графы или широкие колонки. CAP помогает выбирать компромисс между согласованностью и доступностью. ACID нужен там, где критична корректность транзакций.
4. **Как работает пошагово.** При проектировании сначала определяют тип нагрузки: OLTP, OLAP, streaming, архив, графовые связи. Затем выбирают модель: PostgreSQL для транзакций, ClickHouse для аналитики, Redis для кеша, HDFS/S3 для больших файлов. Потом задают требования к согласованности: строгая ACID-транзакция или eventual consistency.
5. **Плюсы.** Правильная модель хранения резко повышает производительность и упрощает разработку. ACID дает надежность транзакций. CAP помогает честно описывать ограничения распределенной системы.
6. **Минусы/ограничения.** Универсального хранилища нет. Сильная согласованность снижает доступность и скорость. NoSQL часто усложняет запросы и транзакции. OLAP-хранилища плохо подходят для частых точечных обновлений.
7. **Реальный кейс.** Интернет-магазин хранит заказы в PostgreSQL с ACID, события кликов в Kafka, агрегированную аналитику в ClickHouse, а большие сырые данные в Data Lake/HDFS.

## 5. HDFS. Архитектура, особенности, сценарии, достоинства и недостатки

**Источник:** `Базы данных в MLOps.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** HDFS, Hadoop Distributed File System, - распределенная файловая система для хранения больших файлов на кластере обычных серверов.
2. **Зачем нужно.** HDFS решает проблему хранения очень больших файлов с отказоустойчивостью и параллельным доступом. Она нужна, когда один диск или один сервер не помещает данные и не обеспечивает нужную скорость чтения.
3. **Архитектура.** Основные компоненты: NameNode, DataNode, блоки данных, репликация. NameNode хранит метаданные: дерево файлов, права, расположение блоков. DataNode хранит реальные блоки. Secondary NameNode не является полноценной горячей заменой NameNode, а помогает с checkpoint метаданных.
4. **Как работает пошагово.** При записи файл разбивается на крупные блоки. Каждый блок записывается на несколько DataNode согласно фактору репликации. NameNode знает, где лежит каждый блок. При чтении клиент спрашивает NameNode о расположении блоков, затем читает данные напрямую с ближайших DataNode. При отказе DataNode система создает недостающие реплики.
5. **Плюсы.** Высокая пропускная способность, масштабирование на дешевых серверах, отказоустойчивость через репликацию, хороший вариант для batch-аналитики и Spark/MapReduce.
6. **Минусы/ограничения.** Плохо подходит для большого числа маленьких файлов, неэффективна для частых обновлений, высокая задержка для интерактивных запросов, зависимость от NameNode, хотя в современных конфигурациях есть HA.
7. **Реальный кейс.** Компания хранит сырые логи за несколько лет в HDFS. Spark ежедневно читает новые партиции, считает агрегаты и выгружает результат в ClickHouse для быстрых аналитических запросов.

## 6. NoSQL. ClickHouse: архитектура, особенности, сценарии, плюсы и минусы

**Источник:** `Базы данных в MLOps.pdf`, `RU_Clickhouse_lecture_2025.pdf`.

1. **Определение.** NoSQL - класс нереляционных хранилищ, которые отходят от строгой табличной модели SQL ради масштабируемости, гибкости схемы или высокой скорости. ClickHouse - распределенная колоночная СУБД для OLAP-нагрузок.
2. **Зачем нужно.** NoSQL нужен, когда реляционная модель слишком жесткая или плохо масштабируется под конкретную нагрузку. ClickHouse нужен для быстрых аналитических запросов по большим объемам данных.
3. **Архитектура.** ClickHouse хранит данные по колонкам, а не по строкам. Использует таблицы семейства MergeTree, партиционирование, сортировку, индексы разреженного типа, сжатие, шардинг и репликацию. Distributed table может направлять запросы на шардированные локальные таблицы.
4. **Как работает пошагово.** Данные загружаются батчами. ClickHouse раскладывает их по колонкам, сортирует по ключу, сжимает и сохраняет в part-файлы. При запросе система читает только нужные колонки и пропускает ненужные диапазоны благодаря сортировке и индексам. В кластере запрос уходит на шарды, частично агрегируется и собирается на координаторе.
5. **Плюсы.** Очень быстрые агрегаты, хорошее сжатие, высокая скорость чтения, удобен для логов, событий, временных рядов, аналитики.
6. **Минусы/ограничения.** Не классическая OLTP-БД, плохо подходит для частых точечных update/delete, eventual consistency в распределенных сценариях, требуется аккуратное проектирование партиций и order by.
7. **Реальный кейс.** Сервис аналитики хранит миллиарды событий пользователей в ClickHouse и за секунды считает DAU, воронки, retention и метрики по рекламным кампаниям.

## 7. SQL и NoSQL. Определения, сравнение, сценарии использования

**Источник:** `Базы данных в MLOps.pdf`.

1. **Определение.** SQL-БД - реляционные СУБД с таблицами, схемой и языком SQL. NoSQL - нереляционные базы: key-value, document, column-family, graph, columnar аналитические и другие.
2. **Зачем нужно.** Разные классы БД решают разные проблемы. SQL удобен для транзакций и структурированных данных. NoSQL удобен для масштабирования, гибкой схемы, больших потоков и специализированных запросов.
3. **Ключевые компоненты.** SQL: таблицы, строки, столбцы, primary key, foreign key, join, transaction, ACID. NoSQL: коллекции/документы, ключи, партиции, репликация, eventual consistency, специфичные API.
4. **Как работает пошагово.** В SQL сначала проектируется нормализованная схема, затем данные пишутся транзакционно и читаются SQL-запросами. В NoSQL модель часто проектируется от запросов: как данные будут читаться, так они и раскладываются по документам, ключам или колонкам.
5. **Плюсы.** SQL дает строгую схему, транзакции, зрелые инструменты, сложные запросы. NoSQL дает масштабируемость, гибкость схемы, высокую скорость для конкретных паттернов.
6. **Минусы/ограничения.** SQL сложнее масштабировать горизонтально и дорого использовать для огромной аналитики. NoSQL может иметь слабую согласованность, ограниченные join, vendor-specific API и более сложное проектирование.
7. **Реальный кейс.** Профили пользователей можно хранить в PostgreSQL, сессии в Redis, документы в MongoDB, граф связей в Neo4j, события аналитики в ClickHouse.

## 8. Гетерогенные СУБД. Greenplum: архитектура, особенности, сценарии, плюсы и минусы

**Источник:** `Базы данных в MLOps.pdf`.

1. **Определение.** Гетерогенные СУБД и MPP-хранилища позволяют работать с распределенными данными и выполнять запросы параллельно на множестве узлов. Greenplum - MPP-аналитическая СУБД на базе PostgreSQL-подхода для больших данных.
2. **Зачем нужно.** Greenplum решает задачу аналитических SQL-запросов по большим объемам структурированных данных, когда один PostgreSQL-сервер уже не справляется.
3. **Архитектура.** Greenplum имеет master/coordinator и segment nodes. Master принимает SQL-запрос, строит план, распределяет работу по сегментам. Сегменты хранят части таблиц и выполняют операции параллельно. Данные распределяются по ключу или случайно.
4. **Как работает пошагово.** Пользователь отправляет SQL-запрос. Master анализирует запрос и строит распределенный план. Сегменты параллельно фильтруют, join-ят и агрегируют свои части данных. Если нужен redistribute, данные перемещаются между сегментами. Master собирает финальный результат.
5. **Плюсы.** SQL-интерфейс, параллельная аналитика, масштабирование по узлам, совместимость с BI-подходами, подходит для Data Warehouse.
6. **Минусы/ограничения.** Нужен правильный distribution key, иначе будут skew и дорогие пересылки. Не оптимален для частых мелких транзакций. Администрирование сложнее обычного PostgreSQL.
7. **Реальный кейс.** Корпоративное хранилище данных собирает продажи, остатки и клиентов из разных систем в Greenplum, где аналитики строят тяжелые SQL-отчеты.

## 9. Типы обработки данных. Grid, WMS, All-Pairs abstractions

**Источник:** `BD_2026_1.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Типы обработки данных описывают способы организации вычислений: Grid - распределение задач по узлам; WMS, workflow management system, - выполнение связанных этапов обработки; All-Pairs - вычисление результата для всех пар объектов.
2. **Зачем нужно.** Эти абстракции помогают формализовать разные классы задач: независимые вычисления, пайплайны и попарные сравнения.
3. **Ключевые компоненты.** Grid: узлы, данные, планировщик. WMS: DAG задач, зависимости, входы/выходы, оркестратор. All-Pairs: набор объектов, функция сравнения пары, механизм параллелизации.
4. **Как работает пошагово.** В Grid задача дробится на независимые части и отправляется на узлы. В WMS сначала строится workflow: например extract -> transform -> train -> validate -> deploy. Система запускает шаги в правильном порядке. В All-Pairs система строит множество пар и параллельно считает метрику между каждой парой.
5. **Плюсы.** Grid хорошо масштабирует независимые задачи. WMS делает pipeline воспроизводимым и управляемым. All-Pairs удобен для similarity search, биоинформатики, дедупликации.
6. **Минусы/ограничения.** Grid плохо подходит для задач с сильными зависимостями. WMS требует описания DAG и контроля состояний. All-Pairs имеет квадратичную сложность O(n^2), поэтому быстро становится дорогим.
7. **Реальный кейс.** ML pipeline в Airflow/Prefect - пример WMS: загрузить данные, предобработать, обучить модель, проверить метрики, выкатить сервис. All-Pairs - поиск похожих документов или изображений.

## 10. Концепция MapReduce вычислений

**Источник:** `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`, `BD_2026_1.pdf`.

1. **Определение.** MapReduce - модель распределенных вычислений, где обработка делится на две основные фазы: Map и Reduce.
2. **Зачем нужно.** MapReduce решает проблему пакетной обработки больших данных на кластере с учетом отказов узлов и распределенного хранения.
3. **Архитектура.** Основные элементы: input split, mapper, shuffle/sort, reducer, output. В Hadoop данные обычно лежат в HDFS, а задачи запускаются рядом с блоками данных.
4. **Как работает пошагово.** Входные данные делятся на части. Mapper обрабатывает каждую часть и выдает пары key-value. Shuffle группирует значения по ключам и передает их reducer-ам. Reducer агрегирует значения по ключу и записывает результат в хранилище.
5. **Плюсы.** Простая модель, высокая отказоустойчивость, хороша для batch-задач, естественно работает с HDFS.
6. **Минусы/ограничения.** Много записи на диск между этапами, высокая задержка, неудобен для интерактивной аналитики, итеративные ML-алгоритмы работают медленно.
7. **Реальный кейс.** WordCount: mapper читает строки и выдает `(word, 1)`, shuffle группирует одинаковые слова, reducer суммирует количества.

## 11. Apache Spark: определение, назначение

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Apache Spark - open-source Big Data фреймворк для распределенной пакетной и потоковой обработки структурированных, слабоструктурированных и неструктурированных данных.
2. **Зачем нужно.** Spark появился как более быстрый и удобный инструмент по сравнению с классическим MapReduce, особенно для итеративных вычислений, SQL, ML и streaming.
3. **Ключевые компоненты.** Spark Core, Spark SQL, MLlib, Structured Streaming, GraphX, Driver, Executors, Cluster Manager, RDD/DataFrame/Dataset API.
4. **Как работает пошагово.** Пользователь пишет приложение. Driver создает SparkContext/SparkSession и строит logical plan/DAG. Cluster Manager выделяет executors. Executors выполняют tasks над partitions. Результат возвращается driver-у или сохраняется во внешнее хранилище.
5. **Плюсы.** Быстрее MapReduce за счет in-memory вычислений, единый API для batch/SQL/ML/streaming, ленивые вычисления и оптимизация планов, поддержка Python/Scala/Java/R.
6. **Минусы/ограничения.** Требует настройки памяти, может падать при skew или нехватке ресурсов, PySpark имеет overhead из-за взаимодействия Python и JVM, не является постоянным хранилищем.
7. **Реальный кейс.** Data engineering pipeline: Spark читает сырые данные из HDFS/S3, очищает, агрегирует, обучает модель или пишет витрину в ClickHouse.

## 12. Apache Spark: особенности

**Источник:** `Введение в Apache Spark.pdf`.

1. **Определение.** Особенности Spark - это свойства, которые делают его универсальным движком обработки больших данных: in-memory, lazy evaluation, DAG scheduler, fault tolerance through lineage, rich ecosystem.
2. **Зачем нужно.** Эти особенности позволяют запускать сложные аналитические и ML-задачи быстрее и удобнее, чем через цепочки MapReduce.
3. **Ключевые компоненты.** RDD/DataFrame, transformations/actions, Catalyst Optimizer для Spark SQL, Tungsten execution engine, cache/persist, broadcast variables, accumulators.
4. **Как работает пошагово.** Spark не выполняет transformations сразу, а строит план. Когда вызывается action, Spark оптимизирует DAG, делит его на stages и tasks, распределяет по executors и выполняет. При необходимости данные кешируются в памяти.
5. **Плюсы.** Высокая скорость, удобные API, поддержка разных типов задач, fault tolerance через lineage, интеграция с HDFS, Hive, Kafka, JDBC.
6. **Минусы/ограничения.** Нужна память; при неправильной настройке возможны OOM; lazy evaluation может скрывать ошибки до action; для streaming с очень низкой задержкой Kafka Streams/Flink иногда подходят лучше.
7. **Реальный кейс.** Ежедневный пересчет признаков для ML: Spark читает миллиарды событий, делает join с профилями пользователей, кеширует промежуточные данные и пишет feature table.

## 13. Apache Spark: архитектура

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Архитектура Spark - распределенная master-worker модель, где Driver управляет приложением, а Executors выполняют задачи на рабочих узлах.
2. **Зачем нужно.** Такая архитектура позволяет распределить вычисления по кластеру и управлять ресурсами централизованно.
3. **Ключевые компоненты.** Driver Program, SparkSession/SparkContext, Cluster Manager, Executors, Tasks, Jobs, Stages, Partitions, DAG Scheduler, Task Scheduler, Block Manager.
4. **Как работает пошагово.** Driver запускает приложение и формирует DAG. Cluster Manager выделяет executors. DAG Scheduler делит граф на stages по границам shuffle. Task Scheduler отправляет tasks на executors. Executors читают partitions, выполняют код и сохраняют результат или возвращают его driver-у.
5. **Плюсы.** Хорошее разделение управления и выполнения, масштабирование по executors, отказоустойчивость, возможность запускаться на Standalone, YARN, Mesos, Kubernetes.
6. **Минусы/ограничения.** Driver - критичная точка управления; если driver перегружен collect-ом больших данных, приложение падает. Shuffle дорогой. Нужна настройка памяти executor/driver.
7. **Реальный кейс.** Spark job на Kubernetes: driver pod создает executor pods, executors читают данные из object storage, выполняют transformations и пишут результат в parquet/ClickHouse.

## 14. Различия между MapReduce и Spark

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** MapReduce - disk-based batch-модель с map/shuffle/reduce. Spark - DAG-based in-memory distributed engine с более широким API.
2. **Зачем нужно сравнение.** Это показывает эволюцию Big Data: от простых batch-задач к интерактивной аналитике, ML и streaming.
3. **Ключевые различия.** MapReduce пишет промежуточные результаты на диск после этапов. Spark может держать промежуточные данные в памяти. MapReduce имеет жесткую модель Map и Reduce, Spark строит произвольный DAG. Spark имеет SQL, MLlib, Streaming, GraphX.
4. **Как работает пошагово.** В MapReduce каждая стадия обычно отдельная job с чтением/записью в HDFS. В Spark цепочка transformations остается в одном DAG и выполняется после action, что уменьшает количество дисковых операций.
5. **Плюсы Spark.** Быстрее на итеративных алгоритмах, удобнее для ML, SQL и интерактивной аналитики, меньше boilerplate.
6. **Минусы Spark.** Требует больше RAM и аккуратной настройки. MapReduce проще и устойчивее для некоторых очень больших batch-задач с ограниченной памятью.
7. **Реальный кейс.** K-means требует многократных проходов по данным. В MapReduce каждый проход пишет на диск, а Spark может кешировать признаки в памяти и ускорить обучение.

## 15. Apache Spark: RDD

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** RDD, Resilient Distributed Dataset, - базовая абстракция Spark: неизменяемая распределенная коллекция объектов, разбитая на partitions и восстанавливаемая через lineage.
2. **Зачем нужно.** RDD позволяет программисту работать с распределенными данными почти как с коллекцией, скрывая детали распределения и отказоустойчивости.
3. **Ключевые компоненты.** Partitions, dependencies, lineage, preferred locations, transformations, actions, persistence levels.
4. **Как работает пошагово.** RDD создается из файла, коллекции или другого RDD. Transformations создают новый RDD, но не выполняются сразу. Action запускает вычисление. Если partition потерян, Spark восстанавливает его по lineage.
5. **Плюсы.** Контроль над низкоуровневыми операциями, fault tolerance, возможность кеширования, гибкость для нестандартной логики.
6. **Минусы/ограничения.** Более низкоуровневый API, чем DataFrame; Spark SQL optimizer не может так эффективно оптимизировать произвольный Python/Scala-код; больше ручной работы.
7. **Реальный кейс.** Нестандартная обработка логов, где нужно применить кастомную функцию к каждой записи, затем сгруппировать и агрегировать результат.

## 16. Apache Spark: трансформация и действие, lineage

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Transformation - операция, создающая новый RDD/DataFrame из существующего, например map, filter, groupBy. Action - операция, запускающая выполнение и возвращающая результат или пишет его наружу, например count, collect, save.
2. **Зачем нужно.** Разделение transformations/actions позволяет Spark строить оптимальный план и выполнять вычисления лениво.
3. **Ключевые компоненты.** Narrow transformations, wide transformations, shuffle, action, DAG, lineage. Lineage - цепочка зависимостей, по которой можно восстановить данные.
4. **Как работает пошагово.** Пользователь пишет `read -> filter -> map -> groupBy -> count`. До `count` Spark только строит план. После action Spark строит DAG, делит его на stages, выполняет tasks и при необходимости делает shuffle.
5. **Плюсы.** Оптимизация всего пайплайна, отказоустойчивость через lineage, меньше лишних вычислений.
6. **Минусы/ограничения.** Ошибки могут проявиться поздно, только на action. Длинный lineage может быть дорогим, тогда нужны checkpoint/cache. Wide transformations вызывают shuffle и могут стать bottleneck.
7. **Реальный кейс.** Для подсчета заказов по регионам Spark сначала фильтрует только успешные заказы, затем группирует по региону. Реальная работа начинается при `write` результата в таблицу.

## 17. Apache Spark: ленивые вычисления, плюсы и минусы

**Источник:** `Введение в Apache Spark.pdf`.

1. **Определение.** Ленивые вычисления означают, что Spark не выполняет transformations сразу, а откладывает выполнение до action.
2. **Зачем нужно.** Это нужно для оптимизации: Spark видит всю цепочку операций и может построить более эффективный план.
3. **Ключевые компоненты.** Logical plan, physical plan, DAG, Catalyst Optimizer для DataFrame/Spark SQL, action trigger.
4. **Как работает пошагово.** Пользователь создает DataFrame, применяет filter/select/join/groupBy. Spark записывает эти операции в план. При `show`, `count`, `collect`, `write` план оптимизируется и выполняется.
5. **Плюсы.** Можно объединять операции, исключать ненужные действия, читать только нужные колонки, перестраивать план для ускорения.
6. **Минусы/ограничения.** Сложнее отлаживать, потому что код вроде бы выполняется, но ошибка появится позже. Можно случайно вызвать тяжелый action. Без cache одна и та же цепочка может пересчитываться повторно.
7. **Реальный кейс.** Аналитик пишет цепочку фильтров и join-ов над parquet. Spark не читает весь parquet сразу, а после `write` читает только нужные колонки и партиции.

## 18. Ленивые вычисления: кэширование

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Кэширование в Spark - сохранение промежуточного RDD/DataFrame в памяти или на диске, чтобы не пересчитывать его при повторном использовании.
2. **Зачем нужно.** Кэш нужен для итеративных алгоритмов, повторных запросов и пайплайнов, где один и тот же набор данных используется несколько раз.
3. **Ключевые компоненты.** `cache()`, `persist()`, storage levels: MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY и др.; Block Manager.
4. **Как работает пошагово.** Пользователь вызывает `df.cache()`. Само кэширование произойдет только после action. Spark вычислит partitions и сохранит их в памяти executors. Следующие actions будут читать данные из cache, если они не вытеснены.
5. **Плюсы.** Ускоряет повторные вычисления, уменьшает нагрузку на storage, полезно для ML и интерактивной аналитики.
6. **Минусы/ограничения.** Кэш занимает память. Если данных больше, чем RAM, возможны eviction, spill на диск и падение производительности. Не надо кэшировать все подряд.
7. **Реальный кейс.** В k-means признаки используются на каждой итерации. Их выгодно подготовить один раз и закэшировать, чтобы не перечитывать исходные данные на каждой итерации.

## 19. Конфигурация Spark приложения

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Конфигурация Spark приложения - набор параметров, определяющих ресурсы, режим запуска, память, число executors, parallelism, shuffle, сериализацию и подключение к внешним системам.
2. **Зачем нужно.** Без настройки Spark может работать медленно, падать по памяти или неэффективно использовать кластер.

Spark передает параметры driver-у и executors. Во время выполнения параметры влияют на распределение tasks, shuffle и memory management.

7. **Реальный кейс.** Для тяжелого groupBy увеличивают `spark.sql.shuffle.partitions`, настраивают executor memory и включают event logging для последующего анализа в Spark History Server.

## 20. Процесс выполнения Spark приложения

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Процесс выполнения Spark приложения - последовательность от запуска driver-а до выполнения jobs, stages и tasks на executors.
2. **Зачем нужно.** Понимание процесса помогает отлаживать производительность, ошибки, shuffle, skew и нехватку ресурсов.
3. **Ключевые компоненты.** Application, job, stage, task, driver, executor, cluster manager, DAG scheduler, task scheduler.
4. **Как работает пошагово.** Пользователь запускает приложение. Driver создает SparkSession. При action создается job. DAG Scheduler строит граф и делит его на stages по shuffle boundaries. Stage делится на tasks по partitions. Tasks отправляются executors. Executors выполняют код, читают/пишут данные и отдают статус driver-у.
5. **Плюсы.** Параллельное выполнение, автоматическое планирование, восстановление failed tasks, масштабируемость.
6. **Минусы/ограничения.** Shuffle и skew могут тормозить весь job. Driver может стать узким местом. Ошибки сериализации и Python/JVM overhead усложняют отладку.
7. **Реальный кейс.** При `df.groupBy("city").count().write.parquet(...)` Spark создает job, делает shuffle по `city`, запускает reduce tasks и записывает итоговые parquet-файлы.

## 21. Использование RDD и кэша во время выполнения Spark приложения

**Источник:** `Введение в Apache Spark.pdf`, `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`.

1. **Определение.** Во время выполнения Spark RDD/DataFrame представляют распределенные данные, а cache/persist позволяет сохранять промежуточные partitions для повторного использования.
2. **Зачем нужно.** Это нужно, чтобы не пересчитывать тяжелые transformations и ускорять повторные actions.
3. **Ключевые компоненты.** RDD partitions, lineage, storage levels, Block Manager, executor memory, unpersist.
4. **Как работает пошагово.** Spark строит lineage RDD. Если пользователь вызывает `cache`, при первом action partitions вычисляются и сохраняются. При следующем action Spark проверяет, есть ли blocks в памяти. Если есть - читает их, если нет - пересчитывает по lineage.
5. **Плюсы.** Значительное ускорение повторных операций, особенно в ML, graph processing и интерактивных сессиях.
6. **Минусы/ограничения.** Кэш конкурирует с execution memory. При нехватке памяти blocks вытесняются. Неиспользуемый cache нужно освобождать через `unpersist`.
7. **Реальный кейс.** Data scientist фильтрует и очищает большой dataset, затем считает несколько моделей/метрик. Очищенный dataset кэшируется, чтобы каждая модель не повторяла всю подготовку.

## 22. Взаимодействие Apache Spark с JVM и интерпретатором Python

**Источник:** `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`, `Введение в Apache Spark.pdf`.

1. **Определение.** Spark написан преимущественно на Scala и работает на JVM. PySpark дает Python API, который взаимодействует с JVM-процессами Spark.
2. **Зачем нужно.** Python популярен в Data Science, поэтому PySpark позволяет использовать Spark без написания Scala/Java-кода.
3. **Ключевые компоненты.** Python driver, Py4J gateway, JVM SparkContext, executors на JVM, Python worker processes, serialization, Arrow для ускорения обмена в некоторых сценариях.
4. **Как работает пошагово.** Python-код вызывает PySpark API. Через Py4J команды передаются в JVM Spark. Driver строит план. Executors выполняют JVM-часть. Если используется Python UDF/RDD map на Python, данные сериализуются и передаются в Python worker на executor-е.
5. **Плюсы.** Удобство Python, доступ к экосистеме pandas/sklearn, возможность использовать Spark в DS-процессах.
6. **Минусы/ограничения.** Python UDF медленнее JVM-native операций из-за сериализации. Ошибки могут быть сложнее. Лучше использовать DataFrame API и встроенные функции Spark SQL, а не Python UDF, если возможно.
7. **Реальный кейс.** ML-инженер пишет PySpark pipeline: читает parquet, делает `select/filter/groupBy` встроенными Spark-функциями, а кастомную Python UDF применяет только там, где нет стандартной функции.

## 23. Spark History Server: организация мониторинга Spark приложений

7. **Реальный кейс.** Spark job стал работать 2 часа вместо 20 минут. В History Server видно, что один stage имеет несколько очень долгих tasks - значит есть data skew при join/groupBy.

## 24. Назначение MLlib, Streaming, SQL, GraphX

**Источник:** `Введение в Apache Spark.pdf`.

## 26. Apache Kafka. Определение. Топики и партиции. Смещение и чтение данных

**Источник:** `apache kafka ru.pdf`, лабораторная 4.

1. **Определение.** Apache Kafka - распределенная платформа потоковой передачи и хранения событий. Она позволяет публиковать, хранить и читать сообщения с высокой пропускной способностью.
2. **Зачем нужно.** Kafka решает проблему надежной передачи событий между сервисами без жесткой связности producer-а и consumer-а.
3. **Ключевые компоненты.** Broker, topic, partition, producer, consumer, consumer group, offset, replication factor, controller, ZooKeeper/KRaft в зависимости от версии.
4. **Как работает пошагово.** Producer отправляет сообщение в topic. Topic разбит на partitions. Сообщение попадает в конкретную partition, часто по key hash. Внутри partition сообщения имеют offset. Consumer читает сообщения и сохраняет offset, чтобы знать, откуда продолжать.
5. **Плюсы.** Высокая throughput, горизонтальное масштабирование через partitions, хранение истории событий, независимость producers и consumers.
6. **Минусы/ограничения.** Порядок гарантируется только внутри partition. Нужна настройка retention, replication, consumer lag. Exactly-once сложнее, чем кажется.
7. **Реальный кейс.** ML-сервис отправляет результат предсказания в Kafka topic, consumer читает сообщения и записывает их в БД или ClickHouse.

## 27. Apache Kafka. Физическая организация партиций, распределение сообщений, хеширование ключей, репликация

**Источник:** `apache kafka ru.pdf`.

1. **Определение.** Partition - физический append-only log внутри topic. Репликация - хранение копий partition на нескольких broker-ах.
2. **Зачем нужно.** Партиции дают масштабирование и параллельное чтение, репликация дает отказоустойчивость.
3. **Ключевые компоненты.** Partition log, segment files, leader replica, follower replicas, ISR, partitioner, message key, replication factor.
4. **Как работает пошагово.** Producer выбирает partition: по key hash или round-robin. Сообщение пишется в leader partition. Followers реплицируют данные. Consumer читает с leader. Если leader broker падает, Kafka выбирает нового leader из ISR.
5. **Плюсы.** Масштабирование записи/чтения, сохранение порядка по ключу внутри partition, устойчивость к отказам broker-а.
6. **Минусы/ограничения.** Неправильный key может создать hot partition. Слишком много partitions увеличивает overhead. Репликация повышает надежность, но требует диска и сети.
7. **Реальный кейс.** Для событий пользователей key=`user_id`, чтобы все события одного пользователя попадали в одну partition и сохраняли порядок.

## 28. Apache Kafka. Гарантии доставки сообщений. Дублирование сообщений

**Источник:** `apache kafka ru.pdf`.

1. **Определение.** Гарантии доставки описывают, сколько раз сообщение может быть обработано: at-most-once, at-least-once, exactly-once.
2. **Зачем нужно.** В распределенных системах возможны сбои producer-а, broker-а или consumer-а. Нужно понимать, потеряются ли сообщения или появятся дубликаты.
3. **Ключевые компоненты.** Producer acks, retries, idempotent producer, transactions, consumer offset commit, isolation level.
4. **Как работает пошагово.** At-most-once: consumer коммитит offset до обработки - дубликатов меньше, но можно потерять сообщение. At-least-once: consumer обрабатывает, потом коммитит offset - потерь меньше, но возможны дубликаты. Exactly-once требует idempotent producer/transactions и корректной обработки sink-а.
5. **Плюсы.** Можно выбрать гарантию под бизнес-задачу. Для аналитики обычно допустим at-least-once с дедупликацией. Для платежей нужны более строгие механизмы.
6. **Минусы/ограничения.** Exactly-once сложен и требует поддержки всей цепочки, включая consumer и storage. Дубликаты часто нужно обрабатывать на уровне бизнес-логики.
7. **Реальный кейс.** События кликов можно обрабатывать at-least-once и дедуплицировать по event_id. Финансовые операции требуют идемпотентных ключей и транзакционной записи результата.

## 29. Apache Kafka. Consumer Groups. Kafka Streams, ksql, Spark Streaming

**Источник:** `apache kafka ru.pdf`, `Введение в Apache Spark.pdf`.

1. **Определение.** Consumer group - группа consumer-ов, совместно читающих topic так, что каждая partition назначается одному consumer-у внутри группы. Kafka Streams, ksqlDB и Spark Streaming - инструменты потоковой обработки Kafka-событий.
2. **Зачем нужно.** Consumer groups масштабируют чтение, а stream processing позволяет обрабатывать события онлайн: фильтровать, агрегировать, join-ить и писать результат.
3. **Ключевые компоненты.** Group coordinator, partition assignment, rebalance, offset commit, state store, windowing, checkpointing.
4. **Как работает пошагово.** Несколько consumers подключаются с одним group id. Kafka распределяет partitions между ними. Если consumer падает или добавляется новый, происходит rebalance. Streaming engine читает события, обрабатывает их по окнам/ключам и пишет результат в topic/БД.
5. **Плюсы.** Горизонтальное масштабирование чтения, независимые группы для разных приложений, возможность real-time аналитики.
6. **Минусы/ограничения.** Внутри одной группы consumer-ов не может быть эффективнее, чем число partitions. Rebalance может временно останавливать обработку. Stateful streaming требует checkpoint/state management.
7. **Реальный кейс.** Одна consumer group считает fraud-score, другая пишет события в ClickHouse, третья обновляет online features для ML-модели.

## 30. ETL/ELT процессы. Хранилища, витрины, озера данных

**Источник:** `1 Intro_ETL_HDFS_ZooKeeper_Spark-overview.pdf`, `Базы данных в MLOps.pdf`.

1. **Определение.** ETL - Extract, Transform, Load: сначала извлечь, преобразовать, затем загрузить. ELT - Extract, Load, Transform: сначала загрузить сырые данные, а преобразовывать уже внутри хранилища. Data Warehouse - структурированное хранилище аналитики. Data Lake - хранилище сырых данных. Data Mart - предметная витрина данных.
2. **Зачем нужно.** Эти процессы нужны, чтобы превратить разрозненные сырые данные в пригодные для аналитики, ML и отчетности наборы.
3. **Ключевые компоненты.** Sources, ingestion, staging, transformation, storage, metadata/catalog, data quality, orchestration, mart.
4. **Как работает пошагово.** В ETL данные извлекаются из источников, очищаются и нормализуются в processing layer, затем загружаются в warehouse/mart. В ELT данные сначала складываются в lake/warehouse, а трансформации выполняются позже SQL/Spark-задачами.
5. **Плюсы.** ETL дает контроль качества до загрузки. ELT сохраняет сырые данные и удобен для масштабируемых cloud/lakehouse-сценариев. Data Mart ускоряет конкретную аналитику.
6. **Минусы/ограничения.** ETL может терять сырой контекст. ELT требует мощного хранилища и дисциплины governance. Data Lake без каталога превращается в data swamp.
7. **Реальный кейс.** Сырые логи попадают в Data Lake, Spark очищает их, агрегаты пишутся в ClickHouse, а витрина продаж используется BI-дашбордом.

## 31. Kubernetes. Контейнерная виртуализация. Архитектура. Pod

**Источник:** `Introduction-to-Kubernetes-RU.pdf`, лабораторная 8.

1. **Определение.** Kubernetes - система оркестрации контейнеров. Контейнерная виртуализация упаковывает приложение и зависимости в изолированный процесс, использующий ядро хоста. Pod - минимальная единица развертывания в Kubernetes.
2. **Зачем нужно.** Kubernetes решает проблему запуска, масштабирования, обновления и восстановления контейнерных приложений в кластере.
3. **Архитектура.** Control Plane: API Server, Scheduler, Controller Manager, etcd. Worker node: kubelet, kube-proxy, container runtime. Объекты: Pod, Service, Deployment, ConfigMap, Secret, Volume.
4. **Как работает пошагово.** Пользователь отправляет YAML в API Server. Объект сохраняется в etcd. Scheduler выбирает node. Kubelet на node запускает контейнеры pod-а через container runtime. Controllers следят, чтобы желаемое состояние совпадало с фактическим.
5. **Плюсы.** Автоматический restart, scaling, rolling updates, service discovery, декларативная модель, переносимость между средами.
6. **Минусы/ограничения.** Высокая сложность, много объектов и сетевых нюансов, требуется мониторинг, безопасность и правильное управление ресурсами.
7. **Реальный кейс.** ML API в Docker разворачивается как Deployment в Kubernetes, получает конфигурацию из ConfigMap, секреты из Secret, а наружу открывается через Service/Ingress.

## 32. Kubernetes. Пространства имен. Метки. Переменные среды

**Источник:** `Introduction-to-Kubernetes-RU.pdf`.

1. **Определение.** Namespace - логическое разделение ресурсов кластера. Labels - key-value метки для выбора и группировки объектов. Environment variables - переменные окружения внутри контейнера.
2. **Зачем нужно.** Namespace изолирует окружения и команды, labels позволяют Kubernetes находить нужные pod-ы, env vars передают конфигурацию приложению.
3. **Ключевые компоненты.** Namespace, label selector, annotations, env, envFrom, ConfigMap, Secret.
4. **Как работает пошагово.** Создается namespace, например `prod`. Deployment получает labels `app=ml-api`. Service использует selector `app=ml-api` и направляет трафик на соответствующие pod-ы. Переменные окружения пробрасываются из ConfigMap/Secret в контейнер.
5. **Плюсы.** Удобная организация кластера, гибкое связывание объектов, отделение конфигурации от image.
6. **Минусы/ограничения.** Namespace не является полной security-изоляцией без RBAC/network policies. Ошибка в labels может сломать routing. Секреты в env могут попасть в логи/дампы.
7. **Реальный кейс.** В namespace `ml-prod` есть pod-ы модели с label `app=model`, Service направляет на них запросы, а `MODEL_PATH` и `DB_HOST` задаются через ConfigMap/Secret.

## 33. Kubernetes. ConfigMap. Resources. QoS. Монтирование Docker volume

**Источник:** `Introduction-to-Kubernetes-RU.pdf`.

1. **Определение.** ConfigMap хранит не секретную конфигурацию. Resources задают requests/limits CPU и памяти. QoS - класс качества обслуживания pod-а. Volume - механизм подключения данных к контейнеру.
2. **Зачем нужно.** Эти механизмы отделяют конфигурацию от image, управляют ресурсами и позволяют сохранять/передавать данные.
3. **Ключевые компоненты.** ConfigMap, Secret, resource requests, resource limits, QoS classes: Guaranteed, Burstable, BestEffort; volumes, volumeMounts.
4. **Как работает пошагово.** ConfigMap создается YAML-ом. Pod подключает его как env или файл. Для контейнера задаются requests/limits. Kubernetes использует requests для scheduling. При нехватке ресурсов QoS влияет на то, какие pod-ы будут вытесняться первыми. Volume монтируется в путь внутри контейнера.
5. **Плюсы.** Гибкая конфигурация без пересборки image, контроль ресурсов, предсказуемее scheduling, возможность подключать файлы и данные.
6. **Минусы/ограничения.** ConfigMap не для паролей. Limits могут приводить к OOMKilled/throttling. Volume без persistent backend может исчезнуть вместе с pod-ом.
7. **Реальный кейс.** Spark driver pod получает настройки через ConfigMap, executor memory задается через resources, а данные модели монтируются через volume.

## 34. Kubernetes. HostPath. PersistentVolume, PersistentVolumeClaim

**Источник:** `Introduction-to-Kubernetes-RU.pdf`.

1. **Определение.** HostPath - volume, который монтирует путь с конкретной node. PersistentVolume, PV, - объект постоянного хранилища в кластере. PersistentVolumeClaim, PVC, - запрос приложения на такое хранилище.
2. **Зачем нужно.** Контейнеры ephemeral: при пересоздании pod-а данные могут исчезнуть. PV/PVC нужны для устойчивого хранения.
3. **Ключевые компоненты.** HostPath, PV, PVC, StorageClass, access modes: ReadWriteOnce, ReadOnlyMany, ReadWriteMany; reclaim policy.
4. **Как работает пошагово.** Администратор создает PV или StorageClass. Разработчик создает PVC с размером и access mode. Kubernetes bind-ит PVC к PV. Pod монтирует PVC как volume и получает постоянный путь.
5. **Плюсы.** Данные переживают restart pod-а, абстракция от конкретного storage backend, декларативное управление.
6. **Минусы/ограничения.** HostPath привязан к node и опасен с точки зрения безопасности. PV/PVC требуют storage backend. Неправильный access mode может заблокировать масштабирование.
7. **Реальный кейс.** База данных в Kubernetes хранит данные на PVC, чтобы при пересоздании pod-а таблицы не исчезли.

## 35. Kubernetes. Pods communication. Service. Multiple Pods. Headless Service. Pod replicas

**Источник:** `Introduction-to-Kubernetes-RU.pdf`.

1. **Определение.** Pods communication - сетевое взаимодействие pod-ов. Service - стабильная точка доступа к набору pod-ов. Headless Service - Service без cluster IP, который возвращает DNS-записи pod-ов напрямую. Replicas - несколько одинаковых pod-ов приложения.
2. **Зачем нужно.** Pod-ы пересоздаются и меняют IP, поэтому нужен стабильный способ обращения к ним и балансировка.
3. **Ключевые компоненты.** ClusterIP, NodePort, LoadBalancer, selector, endpoints, kube-proxy, DNS, headless service, replicas.
4. **Как работает пошагово.** Deployment создает несколько pod-ов с label `app=api`. Service с selector `app=api` находит эти pod-ы и создает endpoints. Клиент обращается к DNS-имени service, а Kubernetes направляет трафик на один из pod-ов. Headless Service возвращает адреса конкретных pod-ов, что полезно для StatefulSet.
5. **Плюсы.** Стабильный DNS, балансировка, масштабирование, service discovery.
6. **Минусы/ограничения.** Service не заменяет полноценный ingress/API gateway. Headless требует, чтобы клиент умел работать с несколькими endpoint-ами. Ошибки readiness/liveness могут сломать маршрутизацию.
7. **Реальный кейс.** Несколько replicas ML API обслуживают запросы. Service `ml-api` балансирует запросы между pod-ами. Stateful Kafka/ZooKeeper использует headless service для стабильной идентичности узлов.

## 36. Kubernetes. ReplicaSet, Deployment, Recreate, Rolling Update, StatefulSet, DaemonSet, Job

**Источник:** `Introduction-to-Kubernetes-RU.pdf`.

1. **Определение.** ReplicaSet поддерживает заданное число replicas. Deployment управляет ReplicaSet и обновлениями. Recreate и Rolling Update - стратегии обновления. StatefulSet управляет stateful-приложениями. DaemonSet запускает pod на каждой node. Job запускает задачу до завершения.
2. **Зачем нужно.** Разные workloads требуют разных контроллеров: stateless API, stateful БД, системные агенты, batch-задачи.
3. **Ключевые компоненты.** ReplicaSet, Deployment, rollout, rollback, strategy, StatefulSet, stable identity, volumeClaimTemplates, DaemonSet, Job, CronJob.
4. **Как работает пошагово.** Deployment создает ReplicaSet, тот создает pod-ы. При обновлении image Deployment создает новый ReplicaSet. Rolling Update постепенно заменяет старые pod-ы новыми. Recreate сначала удаляет старые, потом создает новые. StatefulSet создает pod-ы с устойчивыми именами и PVC. DaemonSet следит, чтобы pod был на каждой node. Job запускает pod до успешного завершения.
5. **Плюсы.** Deployment удобен для stateless сервисов. Rolling Update дает обновления без downtime. StatefulSet подходит для БД и брокеров. DaemonSet полезен для лог-агентов. Job удобен для batch.
6. **Минусы/ограничения.** StatefulSet сложнее администрировать. Rolling Update может временно держать две версии приложения. Recreate дает downtime. Job не предназначен для долгоживущих сервисов.
7. **Реальный кейс.** ML API - Deployment с rolling update. ClickHouse/Kafka - StatefulSet. Node exporter или log collector - DaemonSet. Ежедневная Spark batch-задача - Job или CronJob.

# Универсальный ответ на тест-кейс

Если дают кейс вроде "нужно построить систему обработки больших данных/ML-сервис/аналитику", отвечай так:

1. **Источники данных.** Определить источники: события пользователей, транзакции, логи, файлы, БД, внешние API.
2. **Ingestion.** Для streaming использовать Kafka: topics по типам событий, partitions по user_id/order_id, replication factor 3, consumer groups для разных обработчиков. Для batch использовать ETL/ELT в Data Lake/HDFS.
3. **Хранение.** Сырые данные - HDFS/Data Lake. Транзакционные данные - PostgreSQL/Greenplum. Быстрая аналитика - ClickHouse. Предметные наборы - Data Mart.
4. **Обработка.** Batch и тяжелые join/агрегации - Spark. Streaming - Spark Structured Streaming/Kafka Streams. Для ML - Spark MLlib или отдельный Python service.
5. **ML/MLOps.** Код в GitHub, данные/модели в DVC, окружение через Conda/requirements, API в Docker, тесты, CI/CD через Jenkins, image в registry.
6. **Secrets.** Пароли и токены не в коде: Hashicorp Vault, Kubernetes Secret, env из Secret.
7. **Kubernetes.** Развернуть сервисы как Deployment/StatefulSet. ConfigMap для конфигов, Secret для секретов, PVC для постоянных данных, Service для доступа, HPA при необходимости.
8. **Monitoring.** Spark UI/History Server, Kafka consumer lag, Kubernetes logs/events, метрики latency/error rate, алерты.
9. **Trade-offs.** Kafka дает масштабируемый ingestion, но требует контроля offsets. Spark мощный, но требует памяти. ClickHouse быстрый для OLAP, но не OLTP. Kubernetes удобен для оркестрации, но сложен в эксплуатации.

Короткий пример финальной архитектуры:

```text
Mobile/Web events
-> Kafka topic events_raw, partition by user_id
-> Spark Structured Streaming validates and enriches data
-> raw events to HDFS/Data Lake
-> aggregates to ClickHouse
-> features to Data Mart
-> ML API in Docker on Kubernetes
-> predictions back to Kafka/PostgreSQL
-> monitoring via Spark History Server, Kafka lag, Kubernetes metrics
```
