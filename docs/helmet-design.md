# HelmetWatch: задача и инженерные решения

Система помогает просматривать видеопоток стройплощадки: она выделяет каски, головы без
касок и людей; подтверждённые по времени случаи отсутствия каски попадают в журнал
вместе со снимком. Это учебный прототип с измеримым качеством модели.

## Семантика классов

Источник: [Construction-PPE](https://docs.ultralytics.com/datasets/detect/construction-ppe/).
Из исходной разметки оставлены `helmet`, `no_helmet`, `Person`; классы переименованы в
`helmet`, `no_helmet`, `person` и перенумерованы в 0/1/2. Остальное исключено из задачи.
Область `no_helmet` — явно размеченный объект. Отсутствие `helmet` на кадре не считается
доказательством нарушения. `person` рисуется на кадре, но не является основанием события.

## Правила события

- Детекции `helmet`/`no_helmet` сопоставляются с треками по IoU >= 0.25.
- Противоречащие друг другу боксы одной головы с IoU > 0.5 разрешаются по уверенности.
- Для нового события нужны три подряд наблюдения `no_helmet` на протяжении минимум секунды.
- Пропуск детекции сбрасывает подтверждение кандидата, но активное событие переживает
  короткий пропуск. Исчезновение более чем на 1.5 секунды заканчивает трек с `lost_track`.
- Два наблюдения `helmet` подряд закрывают событие с `helmet_seen`.
- Завершение видеоклиента закрывает события с `stream_ended`. Перезапуск сервера —
  с `server_restart`. Эти причины не означают, что человек надел каску.

Нарушение — это событие по треку головы, а не идентификация человека. Лёгкий IoU-трекер
может терять ID при быстрых движениях, перекрытиях и плотной толпе; переидентификация
и промышленный multi-object tracking здесь не реализованы.

## API и состояние

`/detect` — проверка одиночного изображения без изменения журнала.
`/inspect?camera_id=...&frame_id=...` — кадр видеопотока, детекции, треки и переходы событий.
`frame_id` должен увеличиваться: старый или повторный кадр получает 409, не увеличивая
счётчик подтверждений. Повторы допускаются для 429/503 и ошибок соединения; клиент не
повторяет запрос с неизвестным исходом после read timeout.

Обновление правил и запись SQLite выполняются под общим lock. На ошибке сохранения
состояние правил восстанавливается. Одновременно допускаются два запроса, камеры
изолированы, количество камер ограничено 32. Клиент сообщает окончание потока через
`POST /cameras/{camera_id}/end` и освобождает состояние камеры.

Сервис запускается **в одном worker**. Треки находятся в памяти процесса; SQLite сохраняет
историю событий. Для нескольких workers/серверов нужно вынести состояние треков и
сериализацию кадров либо назначать камеру одному процессу. Не добавлять `--workers 4`
без изменения этой архитектуры.

При остановке камеры без запроса `/end` события могут оставаться открытыми до следующего
кадра этой камеры или перезапуска сервера. Автоматический watchdog — отдельное расширение.

## Данные и качество

Сохраняются официальные train/val/test-разделения. Точные дубликаты изображений по SHA256
исключаются, приоритет — test, затем val, затем train. Это не гарантирует отсутствия
похожих кадров или одинаковых сцен в разных частях: для собственной камеры нужен
отдельный тест на новых видео и разделение по площадке/камере/дню.

Демо-профиль ограничивает размер выборок и предпочитает train-фотографии с `no_helmet`.
Это осознанная учебная выборка для освоения редкого класса. Val/test не балансируются
по меткам. Полный профиль использует весь набор и 640×640.

`best.pt` выбирается по validation во время обучения. Затем выбранная модель оценивается
на test; сохраняются precision, recall, mAP50 и mAP50–95 по каждому классу. Для полного
профиля gate требует mAP50 >= 0.5 и recall `no_helmet` >= 0.6. Это заданные учебные пороги,
а не требования реального объекта. Демо всегда маркируется `experimental`; публикация
релизного образа из такого профиля запрещена в CI.

Recall Ultralytics выводится при выбранной библиотекой рабочей точке; он не равен recall
API при confidence=0.4. Следующий шаг — подобрать порог на val и измерить метрики
событий на размеченных видео: ложные события, пропуски и время подтверждения.

## MLOps

DVC: prepare → train → evaluate → export → benchmark. Датасет, параметры, исходные и
обученные веса связаны через SHA256/fingerprint. Экспорт проверяет соответствие весов
отчёту оценки и размера входа; PyTorch/ONNX parity проверяется отдельно. Экспорт не
подменяет оценку качества.

Docker упаковывает ONNX-модель без PyTorch в runtime. SQLite и снимки хранятся в volume.
Откат выполняется выбором предыдущего image digest; версия модели сохраняется в каждом
событии. После смены версии старые треки не используются для подтверждения новых событий.
